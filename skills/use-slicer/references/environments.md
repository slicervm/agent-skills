# Project environments with slicer env

Use `slicer env` for a repeatable project development environment: a real Linux
VM containing the application's dependencies, workspace, and long-running
services. This is Slicer's project-level alternative to a Dockerfile plus
Docker Compose. Several services run as systemd units in one VM; each service
is not a separate container or VM. Native `slicer vm` commands remain useful
for inspecting and operating that VM.

## Start with the project's config

Look for a project `slicer.yaml` before constructing an ad hoc VM workflow.
Run env commands from the directory containing that file; commands do not
search parent directories. This is a different schema from the daemon's
`slicer.yaml` generated by `slicer new` (`config.host_groups`). Keep the two
files in separate directories.

A running Slicer daemon is required. Use the same API URL and credentials for
all commands, preferably through `SLICER_URL` and `SLICER_TOKEN_FILE`. Pass
`--hostgroup GROUP` to `env up` when group selection is ambiguous.

Environments are discovered by config `name`, client hostname, and local user
tags. Keep those consistent. Two checkouts using the same name on the same
machine as the same user share an environment; choose different names when
they need independent VMs. Avoid switching casually between `slicer` and
`sudo slicer`, which can change the user used for discovery.

## Config and lifecycle

Example for a small static site:

```yaml
name: site-preview
setup: |
  apt-get update -qy
  apt-get install -qy --no-install-recommends python3
init: |
  test -f index.html
services:
  - name: web
    command: exec python3 -m http.server 8000 --bind 0.0.0.0
    env:
      PYTHONUNBUFFERED: "1"
ready:
  http: http://localhost:8000
  timeout: 60s
forward:
  - "8000:8000"
exclude:
  - .git
  - node_modules
  - "*.img"
```

- `setup`: root userdata, run when creating the VM, before workspace upload.
  Install OS dependencies here. It cannot read project files that have not
  been copied yet.
- `init`: runs in the copied workspace as the guest user after setup.
  Install project dependencies here, for example `bundle install` or `npm ci`.
- `services`: long-running processes. `command` units run as `ubuntu` with the
  workspace as their working directory; `env` provides their environment.
  Units are named `slicer-env-NAME.service` and restart on failure. Use `raw`
  for a complete custom systemd unit instead of `command`.
- `ready`: HTTP or exec readiness check inside the guest, with a timeout.
- `forward`: local-to-guest port mappings. Check local port availability.
- `exclude`: copy exclusions, merged with `.slicerignore` and default workspace
  exclusions. Put generated output, caches, and unwanted local files here.
- `fetch`: optional files to retrieve after initial setup/readiness. Entries
  support `remote:local`; relative paths are relative to the workspace.

For a Jekyll site such as `openfaas/openfaas.github.io`, use the repository's
existing config: Ruby/build packages in `setup`, Bundler dependencies in
`init`, and `bundle exec jekyll serve --force_polling ...` as a service.
Exclude `_site`, dependency caches, and the daemon's files from uploads.

```bash
slicer env up --hostgroup GROUP
slicer env status --json
slicer env shell
slicer env push
slicer env push --watch
slicer env push --run-init --restart-services
slicer env forward
slicer env pull
slicer env down
```

`env up` creates the VM, waits for setup, copies the workspace, runs init,
installs services, checks readiness, and fetches configured files. If an env
VM already exists, it reports that VM and returns; it does not reconcile
config edits or push updated source. Use `env push` for later source changes.

`env up` does not currently request a persistent API VM. Do not treat an env
VM as durable storage across guest shutdown or daemon restart. `env down`
deletes the VM and its data. Retrieve wanted work before teardown.

## Editing and synchronising

The local project directory maps to its equivalent under `/home/ubuntu` in
the VM. For example, `~/projects/site` maps to `/home/ubuntu/projects/site`.
The guest service reads that workspace; there is no shared host bind mount.

- `env push`: copies the workspace contents into that exact guest directory,
  honouring exclusions, then fixes ownership. This is a full copy, not an
  rsync-style comparison. It does not delete guest-only files.
- `env push --watch`: performs the same initial full copy, then watches local
  regular files. Size/mtime changes trigger uploads after a 500 ms debounce;
  observed file deletions are propagated. Changes made before watch starts
  rely on the initial full copy. Stop with Ctrl+C. Watch is not bidirectional.
- `--run-init`: reruns init after syncing, useful for changed dependencies.
- `--restart-services`: restarts existing units after syncing. It does not
  rewrite units from edited YAML or rerun setup. For changed service/unit
  definitions, explicitly deploy the updated unit or recreate the disposable
  environment after retrieving wanted data.
- `env pull`: copies the guest workspace contents back into the local project,
  honouring exclusions. It can overwrite local edits; it is not a merge.
  For one generated artifact, use `slicer vm cp` with the VM from env status.

For services with their own file watcher (Jekyll, Vite, etc.), ordinary push
or watch is usually enough; restarting on every edit is unnecessary. Run
`env push --watch` in a tracked terminal or tmux session when it must stay
active, and stop that exact process when finished.

### Diagnosing an apparently successful stale push

Older clients can report `sent 0 B` for every directory upload even when data
was sent. This is not evidence that files are already synchronised. Some
clients also apply directory-copy semantics that put repeat uploads into
`workspace/project-name/`, leaving the service's original files unchanged.
Watch's per-file updates can mask that problem after a later edit.

Verify the changed file at the service's actual working directory and compare
its contents or hash with the local file. Check exclusions and unexpected
nested project directories before blaming the application's file watcher.
Use a client containing the workspace-content copy fix; do not treat
`--watch` as a reliable repair for an already-stale initial upload. Inspect
old nested copies before removing them, as they may contain wanted changes.

## Forwarding and diagnosis

On macOS, `env up` starts configured forwarding and remains attached. On
Linux, a fresh `env up` with only TCP forwards currently prints direct guest
URLs; it does not start a localhost forward. Use `env forward` explicitly
for localhost access, remote daemons, or isolated networking. It blocks until
interrupted. Ending a forward does not tear down the VM or systemd services.

Use `env status --json` for the VM identity, service states, and readiness;
`env list --json` lists environments. Inspect the service inside the VM:

```bash
slicer vm exec VM_REF --uid 0 -- systemctl status slicer-env-web.service
slicer vm exec VM_REF --uid 0 -- journalctl -u slicer-env-web.service -n 80 --no-pager
```

If a stopped VM is still listed, `env up` currently reports the existing VM;
it does not automatically relaunch it. Check whether it is persistent and
use `slicer vm relaunch` when appropriate. Do not delete existing project
state merely to resolve a status or forwarding problem.
